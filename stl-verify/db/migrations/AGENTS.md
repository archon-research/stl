# Database & migrations

Schema, migration, and snapshot-read rules for stl-verify. These load when you work under
`stl-verify/db/migrations/`; they also apply when writing repository adapters
(`internal/adapters/outbound/**/*repository*.go`), so read them for that work too.

- Always think hard and carefully about how the wrong data could be written to the database.
- Always think hard and carefully about schema design.
- Full auditability: any value that can change over time (on-chain state, governance-settable config — fees, caps, rates, recipients) is stored append-only with the version tuple (`block_number`, `block_version`, `processing_version`), so "what was X at block N" is answerable with a plain SELECT. In-place mutable columns are reserved for genuinely immutable identity facts (addresses, decimals, deploy blocks) — and nothing else. A "set-once lifecycle field" is **not** exempt: a close block, a de-registration, an `is_active` flag are observations like any other and are appended, not written into the row they close (see the strict append-only rule below). "Reconstructible by decoding raw `protocol_event` payloads" does not satisfy this — history must be structurally queryable. Versioning also buys reorg-rollback and replay-order-independence for free; a mutable cell has neither (no `block_version` to roll back, and last-write-wins lets a backfill replay regress newer live values). An `UPDATE` that sets a time-varying field on an ingest path is a review finding, even when a ticket specifies it.
- **Strictly append-only.** Ingest paths INSERT. They never UPDATE, never DELETE, and never `INSERT … ON CONFLICT … DO UPDATE` — not even the no-op `SET id = t.id` used to make `RETURNING` fire, because the `DO UPDATE` arm requires UPDATE privilege and is refused at executor start whether or not a conflict occurs (a plain `EXPLAIN` of it is refused too). Use `ON CONFLICT DO NOTHING` and a follow-up `SELECT` instead; under READ COMMITTED that is race-free, because `DO NOTHING` waits out the conflicting transaction. Identity rows — a surrogate id, a natural key, and genuinely immutable facts — are written once and never converged; everything else, **lifecycle included** (membership, activation, removal, classification), is an appended observation carrying the version tuple, and "what is X now" is `ORDER BY block_number DESC, block_version DESC[, log_index DESC], processing_version DESC LIMIT 1`, never a column. Tables are converted one at a time; a converted table's creating migration ends with `REVOKE UPDATE, DELETE ON <table> FROM stl_readwrite;` — the DB-level enforcement, which TimescaleDB propagates to a hypertable's chunks, present and future. `TestConvertedTablesAreAppendOnly` (db/migrator) asserts the grants for the converted set. A `DO UPDATE`, an `UPDATE` or a `DELETE` in a repository adapter is a review finding; on a converted table it is a runtime error. Converted so far: `morpho_adapter`, `morpho_adapter_membership`, `morpho_adapter_state`, `morpho_vault_cap`, `morpho_vault_fee`, `psm3_alm_shares` (append-only from birth, ARCT-217), `position_state` (append-only from birth, VEC-402), `position_projection_run` (append-only from birth, VEC-401), `asset_price` (append-only from birth, VEC-652), and the ten `uniswap_v4_*` tables — `uniswap_v4_pool_manager`, `uniswap_v4_pool`, `uniswap_v4_pool_state`, `uniswap_v4_swap`, `uniswap_v4_liquidity_event`, `uniswap_v4_tick`, `uniswap_v4_pool_event` (append-only from birth, VEC-475), `uniswap_v4_position` (append-only from birth, VEC-572), `uniswap_v4_position_manager` and `uniswap_v4_position_nft_transfer` (append-only from birth, ARCT-385), and the combined master's `sec_node` and `sec_edge` (append-only from birth, VEC-617 — the owner's privileges revoked as well, as `position_state` already does, and safe on all three because nothing FKs them; these two derive the owner from `pg_class.relowner` rather than naming `stl_migrator`, so the revoke fires in CI too. Their governed vocabularies are FK parents, so the owner keeps UPDATE for the integrity probe and append-only there is the `reference_table_immutable()` trigger instead), `block_meta` (append-only from birth, VEC-491), and the two CORE reference tables `reference_core_market_result` and `reference_core_vault_result` (append-only from birth, VEC-828).
- **Append-only is the DEFAULT, for every table — not just the converted set.** Adding ANY update channel — a table-wide or column-scoped `GRANT UPDATE`, an `ON CONFLICT … DO UPDATE` arm, an in-place rewrite of any non-identity column — requires consulting the team FIRST, before it ships. A sanctioned update channel must be recorded in this file as an explicit exception citing the ticket; an unconsulted or unrecorded one is a review finding regardless of scope or how narrow the column grant is. Corrections belong in new `block_version`/`processing_version` rows, not rewrites.
- **Sanctioned update channel: the trigger-maintained `*_current` derived caches** — `borrower_current`, `borrower_collateral_current`, `sparklend_reserve_data_current`, `token_price_current` (VEC-577, `20260820_120000`), `allocation_position_current` (VEC-660, `20260825_120000`), `morpho_market_position_current` (VEC-753, `20260909_150000`), and `morpho_vault_state_current` + `morpho_market_state_current` (VEC-659, `20260910_140000`). They take an `ON CONFLICT … DO UPDATE` arm because they are derived caches of the newest-row query over append-only history: the history stays untouched, every row is reproducible by re-running the backfill, and they are never read as history (no "as of block N" answer in them). Their newer-wins comparison orders identity terms first and `processing_version` LAST, with any table-specific identity tiebreak (`direction`, `tx_hash` on `allocation_position_current`) still ahead of it — `processing_version` versions one row, so it must never rank rows of differing identity against each other. The channel is a FUNCTION, not a role privilege: `allocation_position_current` is written only by its `SECURITY DEFINER` trigger and the migrator's backfill, both running as the owner, and `stl_readwrite` holds `SELECT` only — its migration `REVOKE`s the `INSERT, UPDATE, DELETE` that `ALTER DEFAULT PRIVILEGES` hands every migrator-owned table (`TestTriggerOnlyCachesGrantTheAppRoleNoWrite`). The four VEC-577 caches still carry the older `GRANT INSERT, UPDATE` form; aligning them is a follow-up.
- **Sanctioned update channel: `position_current`** (VEC-409, `20260819_150000`) — a derived cache of the newest `position_state` observation per position; the history stays untouched and every row is reproducible with `CALL rebuild_position_current()`. Written only by its `SECURITY DEFINER` trigger, which runs as the owner, and by `rebuild_position_current()`, which is invoker-rights and so is owner-only in practice: `stl_readwrite` holds `SELECT` only, enforced by `TestTriggerOnlyCachesGrantTheAppRoleNoWrite`. Its limits — a lower-block reorg replacement, and the forward-only rebuild's two unrepairable classes — are recorded in the table `COMMENT`.
- **A time window on a hypertable is a SQL literal, never a bind parameter.** `WHERE ts > now() - interval '7 days'` is constified at plan time and excludes every chunk outside the window; `WHERE ts > now() - CAST(:age AS interval)` is not, so the planner builds paths for every chunk and the backend keeps their metadata — the CORE feed-liveness check planned all 355 chunks of `onchain_token_price` this way (21.8 MB / 754 ms of planning against 100 kB / 0.4 ms with the literal; VEC-672). A window that comes from config is interpolated as a literal; a window that comes from a caller is validated and then interpolated, never bound. And a latest-row read that has no window at all belongs on a `*_current` cache, not on the history.
- **Sanctioned update channel: `backfill_watermark`** (ARCT-379, `20260831_120000`). One row per chain holding an operational cursor — how far the gap filler has verified — not history: it is never read as "as of block N", and its value is fully reproducible from `block_states` by re-running the gap scan. Four writers, and no other: (1) the gap filler's compare-and-set advance (`AdvanceBackfillWatermark`), which writes only while the stored `(watermark, rewind_count)` pair is still the one its scan was computed from, and never writes `rewind_count` itself — it matches on it; (2) `HandleReorgAtomic`'s reorg commit, which lowers the watermark to the common ancestor with `LEAST` and bumps `rewind_count` whether or not the watermark moved; (2b) the backfill service's rewind before it empties a height (`RewindBackfillWatermark`: stale-chain recovery, retry reconcile, post-save linkage orphan), the same `LEAST`-and-bump write as (2), taken under `FOR UPDATE` in its own transaction; (3) an operator's raw SQL from the runbook, which must bump `rewind_count` alongside the watermark or a pass already scanning will advance straight back over the re-opened height. The `rewind_count` exists because the rewind is frequently a no-op — the watermark normally trails head by one, exactly where a common ancestor lands — so a compare-and-set on the watermark alone matched across a reorg and retired the hole it had just opened. No unconditional writer is exposed on the port; tests seed the row with SQL. The column `COMMENT` names all four (`20260831_120000`).
- **Sanctioned delete channel: `block_meta_worklist`** (VEC-491, `20260911_130000`). Run scratch, not history: the blocks a chain references that `block_meta` lacks, enumerated per run and paged with a keyset cursor. Never read as of a block, and every row is reproducible by re-running the enumeration, which is why it is `UNLOGGED`. One writer, the block-meta loader, which owns the whole lifecycle — it clears its own chain at the start of every run and no other process writes it. `stl_readwrite` holds `SELECT, INSERT, DELETE` and no `UPDATE`; the version-tuple discipline does not apply because nothing here is an observation.
- TimescaleDB primitives belong on tables that have earned them (see the create-plain rule below). Foreign keys from a hypertable to a regular table work, compressed chunks included, and are expected. Never point a foreign key at a hypertable: it pins every chunk and blocks `drop_chunks`.
- Reading latest snapshot rows: state/snapshot tables carry `build_id` (audit-only: which deployment wrote the row) and `processing_version` (correction version: 0=original, N=Nth reprocess). To select the current/latest row per entity, order by the table's snapshot-time key — `block_number, block_version` for on-chain tables, `synced_at`/`timestamp`/`snapshot_time` for API-sourced — `DESC`, then `processing_version DESC`. NEVER use `build_id` to pick latest: it appears in no unique constraint and one `build_id` spans many sync cycles, so ordering by it picks an arbitrary cycle and mixes values across cycles (manufactures fake anomalies).
- Interpreting numeric columns: a column's name and magnitude don't determine its unit or scale — verify against the column `COMMENT` (psql `\d+ <table>`) or the domain entity doc before computing, aggregating, or flagging an anomaly. Conventions vary per column: raw native-decimal ints (scale by `token.decimals`), column-specific fixed-point (`maple_loan_collateral.asset_value_usd` = per-unit USD price ×1e8, not a total; `maple_loan_state.acm_ratio` = ratio ×1e6), already-normalized decimals (`onchain_token_price.price_usd`), or values that aren't what the name implies (`allocation_position.scaled_balance` = interest-free reading, not the balance). A value repeated across rows is usually correct (one per-unit price per asset per snapshot), not corruption.
- Document every new table and column with `COMMENT ON` in the same migration that creates it — these are the catalogue's source of truth and what the "Interpreting numeric columns" rule above reads. A `--` inline comment is not enough; it is invisible to `\d+` and the metadata catalogue. Match the established style from `20260609_120000_add_schema_comments.sql`: a `[Type]` tag (`Dimension` | `Configuration` | `Operational` | `Timeseries` | `Hypertable`) on the table — a new time-series table is `Timeseries`, and becomes `Hypertable` only in the migration that converts it; per-column `Roles` (`PK` | `FK→table.col` | `Derived` | `Partition` | `Audit`); and, for any numeric column, its exact unit/scale (raw native-decimal int vs fixed-point ×1eN vs normalized). A column whose unit/scale is not self-evident from its type MUST state it.
- Read-then-write races: when an insert decision depends on a prior read of the same key (read-latest-then-insert, MAX(version)+1, append-on-change), serialize concurrent writers with `pg_advisory_xact_lock` on the natural key — `ON CONFLICT` alone cannot guard a decision made before the insert (ADR-0002 §3); acquire locks in sorted key order to stay deadlock-free.
- A `BEFORE INSERT` trigger function that runs a per-row lookup against a hypertable — every `assign_processing_version_*` function does — must include `SET plan_cache_mode = 'force_custom_plan'` in the `CREATE FUNCTION` that declares it, in the same migration: plpgsql switches the cached lookup to a generic plan after ~5 executions, and a generic plan prunes chunks only where TimescaleDB's `ChunkAppend` can still exclude them at runtime — a `MAX(...)` lookup plans as a `Merge Append` and fans out over every chunk — so insert cost grows with the table's total chunk count (measured 4,410 ms vs 148 ms for one 721-row batch at ~2,000 chunks). The trigger fires before `ON CONFLICT` resolves, so that floor is paid even for the rows the insert then discards. `CREATE OR REPLACE FUNCTION` resets a function's settings, so re-declare the SET whenever you replace one of these functions; `TestProcessingVersionTriggersForceCustomPlan` enumerates `pg_proc` and fails if any of them lacks it (VEC-541, ADR-0002 §3).
- NEVER modify an applied migration file in `stl-verify/db/migrations/`: the migrator tracks checksums and will reject modified files. Always create a new migration file for fixes or additions. The one exception is a transactional migration (no `-- migrate: no-transaction`) that failed on every persistent environment: its self-registering `INSERT` is its last statement, so nothing recorded it, and it is corrected in place rather than left to fail forever (#527, #826, #898). A local kind DB that did record it fails checksum verification and needs `make dev-wipe`.
- Filename format: `YYYYMMDD_HHMMSS_description.sql`; plain SQL, applied automatically in order.
- Every migration must self-register: end it with `INSERT INTO migrations (filename) VALUES ('<filename>') ON CONFLICT (filename) DO NOTHING;` or it re-runs on every invocation. Don't mask that with an idempotency guard.
- **Create every table plain; convert it to a hypertable in a later migration, once measurement says to.** A chunk interval, a `segmentby`/`orderby` pair and a tiering horizon are bets on ingest rate and read shape, and measurement settles them afterwards; converting stays cheap because it is in-place — `create_hypertable(…, migrate_data => true)` keeps the FK, the secondary indexes, the `processing_version` trigger and the grants. Compression and tiering policies land in that conversion migration, and so do the two traps below. Confirm the hot reads prune chunks before shipping one; `docs/runbooks/vector-indexers.md` § `VectorUniswapV4AppendOnChangeGrowthHigh` is the worked example. Existing hypertables stay as they are.
- A plain table ships with a row-growth alert and a runbook section holding its conversion path — that alert is what notices it growing (`VectorUniswapV3/V4AppendOnChangeGrowthHigh`, VEC-572, are the template). Its `COMMENT` records that it is plain and what would change that.
- Three tables stay plain permanently: `uniswap_v3_tick`, `uniswap_v4_tick` (VEC-475) and `uniswap_v4_position` (VEC-572). Their write path reads the latest row per key *at or below a block height*, a bound partitioning prunes nothing on, so it pays the VEC-541 fan-out on the per-block path; and tiering makes that comparison read miss any row past the horizon (`timescaledb.enable_tiered_reads` defaults off), so the writer appends a change that never happened. Their `COMMENT` says so.
- Compression policy trap: `CREATE TABLE ... WITH (tsdb.hypertable, ...)` auto-enables the columnstore AND auto-creates a 1-day compression policy at CREATE time; a later `add_compression_policy(..., if_not_exists => TRUE)` then returns -1 and silently keeps the 1-day auto-policy — the interval you wrote never takes effect (VEC-570: this bit 12+ staging tables). Declare `tsdb.columnstore = false` in the CREATE, then configure compression and the policy explicitly, and assert the *effective* policy interval in the migration test (see `20260819_120000_create_uniswap_v4_tables.sql`). Never end up with two policy jobs on one hypertable — the earlier threshold wins.
- Tiering round-trip trap: on Tiger Cloud, `add_tiering_policy` attaches an OSM chunk that arrives with the hypertable's CHECK constraints re-created from their deparsed text, and PostgreSQL refuses the attach unless each constraint deparses to the same text as the parent's (`child table "osm_chunk_N" has different definition for check constraint`, 42804). Two shapes are known to fail: a BETWEEN-family operator as the first operand of an `AND`/`OR` chain whose operator it expands to (`x BETWEEN a AND b AND …`, `x NOT BETWEEN a AND b OR …` — the stored tree keeps the nested node, the re-parse flattens it; VEC-475, 2026-09-07: `20260819_120000` blocked every staging deploy), and an `IN`-list CHECK on a `VARCHAR` column (its casts do not round-trip; #527 moved `curve_liquidity_event.kind` to `TEXT`). Write the first as flat comparisons (`x >= a AND x <= b AND …`; a `BETWEEN` anywhere else in the chain, or on its own, is fine) and put the second on `TEXT`. Only staging and prod see it — the local harness has no tiering and skips the policy — so `TestHypertableCheckConstraintsSurviveTheTieringRoundTrip` (db/migrator) performs the same attach against plain-table clones of every hypertable; it reproduces both shapes.
- `block_states` deliberately has NO compression policy: it is the workers' hot read-path cache (rows re-read and versioned on reorgs) and stays rowstore. Don't "fix" its missing policy.
- Role admin vs object grants: role-level ops (`CREATE ROLE`, `ALTER ROLE … SET`, role-to-role membership grants) require superuser and belong in the infra repo's `bootstrap-db.sh`. Migrations run as `stl_migrator` (CREATEROLE only) and hold object-level grants only (`GRANT … ON <object> TO <role>`, `ALTER DEFAULT PRIVILEGES`). Rule: a role named on the left of ALTER/GRANT/DROP = bootstrap; object on left, role on right = migration.
