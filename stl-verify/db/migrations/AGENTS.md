# Database & migrations

Schema, migration, and snapshot-read rules for stl-verify. These load when you work under
`stl-verify/db/migrations/`; they also apply when writing repository adapters
(`internal/adapters/outbound/**/*repository*.go`), so read them for that work too.

- Always think hard and carefully about how the wrong data could be written to the database.
- Always think hard and carefully about schema design.
- Full auditability: any value that can change over time (on-chain state, governance-settable config — fees, caps, rates, recipients) is stored append-only with the version tuple (`block_number`, `block_version`, `processing_version`), so "what was X at block N" is answerable with a plain SELECT. In-place mutable columns are reserved for genuinely immutable identity facts (addresses, decimals, deploy blocks) — and nothing else. A "set-once lifecycle field" is **not** exempt: a close block, a de-registration, an `is_active` flag are observations like any other and are appended, not written into the row they close (see the strict append-only rule below). "Reconstructible by decoding raw `protocol_event` payloads" does not satisfy this — history must be structurally queryable. Versioning also buys reorg-rollback and replay-order-independence for free; a mutable cell has neither (no `block_version` to roll back, and last-write-wins lets a backfill replay regress newer live values). An `UPDATE` that sets a time-varying field on an ingest path is a review finding, even when a ticket specifies it.
- **Strictly append-only.** Ingest paths INSERT. They never UPDATE, never DELETE, and never `INSERT … ON CONFLICT … DO UPDATE` — not even the no-op `SET id = t.id` used to make `RETURNING` fire, because the `DO UPDATE` arm requires UPDATE privilege and is refused at executor start whether or not a conflict occurs (a plain `EXPLAIN` of it is refused too). Use `ON CONFLICT DO NOTHING` and a follow-up `SELECT` instead; under READ COMMITTED that is race-free, because `DO NOTHING` waits out the conflicting transaction. Identity rows — a surrogate id, a natural key, and genuinely immutable facts — are written once and never converged; everything else, **lifecycle included** (membership, activation, removal, classification), is an appended observation carrying the version tuple, and "what is X now" is `ORDER BY block_number DESC, block_version DESC[, log_index DESC], processing_version DESC LIMIT 1`, never a column. Tables are converted one at a time; a converted table's creating migration ends with `REVOKE UPDATE, DELETE ON <table> FROM stl_readwrite;` — the DB-level enforcement, which TimescaleDB propagates to a hypertable's chunks, present and future. `TestConvertedTablesAreAppendOnly` (db/migrator) asserts the grants for the converted set. A `DO UPDATE`, an `UPDATE` or a `DELETE` in a repository adapter is a review finding; on a converted table it is a runtime error. Converted so far: `morpho_adapter`, `morpho_adapter_membership`, `morpho_adapter_state`, `morpho_vault_cap`, `morpho_vault_fee`, `psm3_alm_shares` (append-only from birth, ARCT-217), `position_state` (append-only from birth, VEC-402).
- **Append-only is the DEFAULT, for every table — not just the converted set.** Adding ANY update channel — a table-wide or column-scoped `GRANT UPDATE`, an `ON CONFLICT … DO UPDATE` arm, an in-place rewrite of any non-identity column — requires consulting the team FIRST, before it ships. A sanctioned update channel must be recorded in this file as an explicit exception citing the ticket; an unconsulted or unrecorded one is a review finding regardless of scope or how narrow the column grant is. Corrections belong in new `block_version`/`processing_version` rows, not rewrites.
- **Sanctioned update channel: the trigger-maintained `*_current` derived caches** — `borrower_current`, `borrower_collateral_current`, `sparklend_reserve_data_current`, `token_price_current` (VEC-577, `20260820_120000`) and `allocation_position_current` (VEC-660, `20260825_120000`). They take an `ON CONFLICT … DO UPDATE` arm because they are derived caches of the newest-row query over append-only history: the history stays untouched, every row is reproducible by re-running the backfill, and they are never read as history (no "as of block N" answer in them). Their newer-wins comparison orders identity terms first and `processing_version` LAST, with any table-specific identity tiebreak (`direction`, `tx_hash` on `allocation_position_current`) still ahead of it — `processing_version` versions one row, so it must never rank rows of differing identity against each other. The channel is a FUNCTION, not a role privilege: `allocation_position_current` is written only by its `SECURITY DEFINER` trigger and the migrator's backfill, both running as the owner, and `stl_readwrite` holds `SELECT` only — its migration `REVOKE`s the `INSERT, UPDATE, DELETE` that `ALTER DEFAULT PRIVILEGES` hands every migrator-owned table (`TestTriggerOnlyCachesGrantTheAppRoleNoWrite`). The four VEC-577 caches still carry the older `GRANT INSERT, UPDATE` form; aligning them is a follow-up.
- **Sanctioned update channel: `position_current`** (VEC-409, `20260819_150000`) — a derived cache of `ORDER BY block_number DESC, block_version DESC, processing_version DESC, block_timestamp DESC LIMIT 1` over `position_state`, which is in the converted set above and stays untouched. It holds `UPDATE` and takes `ON CONFLICT … DO UPDATE`, carried identically by both writers — the statement trigger `trigger_upsert_position_current` and the backfill statement in `20260819_150100` — so whichever resolves second is a guarded no-op. `DELETE` is explicitly revoked. The limits are recorded in its migration's table `COMMENT`, not just here: a lower-block reorg replacement does not displace the orphan it supersedes, and re-running the backfill statement is a FORWARD-ONLY merge — it raises a cached row to a newer observation and converges one whose payload drifted at coordinates EQUAL to history, but never lowers or removes one, so it cannot repair a row ahead of history (repairable in-role by a plain `UPDATE`) or an orphan row whose position has no history (owner-only: `DELETE` is revoked and `TRUNCATE` was never granted). Those two are the whole list only because equal coordinates converge; the comparison is `IS DISTINCT FROM`, not `<>`, since `chain_id` and `protocol_id` are nullable. Point-in-time questions are answered from the history table. Its trigger function is `SECURITY INVOKER` and `stl_readwrite` holds `GRANT INSERT, UPDATE`, so it carries the older form named above rather than the trigger-only shape, and the same alignment follow-up applies.
- **Sanctioned update channel: `backfill_watermark`** (ARCT-379, `20260831_120000`). One row per chain holding an operational cursor — how far the gap filler has verified — not history: it is never read as "as of block N", and its value is fully reproducible from `block_states` by re-running the gap scan. Four writers, and no other: (1) the gap filler's compare-and-set advance (`AdvanceBackfillWatermark`), which writes only while the stored `(watermark, rewind_count)` pair is still the one its scan was computed from, and never writes `rewind_count` itself — it matches on it; (2) `HandleReorgAtomic`'s reorg commit, which lowers the watermark to the common ancestor with `LEAST` and bumps `rewind_count` whether or not the watermark moved; (2b) the backfill service's rewind before it empties a height (`RewindBackfillWatermark`: stale-chain recovery, retry reconcile, post-save linkage orphan), the same `LEAST`-and-bump write as (2), taken under `FOR UPDATE` in its own transaction; (3) an operator's raw SQL from the runbook, which must bump `rewind_count` alongside the watermark or a pass already scanning will advance straight back over the re-opened height. The `rewind_count` exists because the rewind is frequently a no-op — the watermark normally trails head by one, exactly where a common ancestor lands — so a compare-and-set on the watermark alone matched across a reorg and retired the hole it had just opened. No unconditional writer is exposed on the port; tests seed the row with SQL. The column `COMMENT` names all four (`20260831_120000`).
- For timeseries tables, use Tigerdata primitives, and make sure they support distributed tables.
- Reading latest snapshot rows: state/snapshot tables carry `build_id` (audit-only: which deployment wrote the row) and `processing_version` (correction version: 0=original, N=Nth reprocess). To select the current/latest row per entity, order by the table's snapshot-time key — `block_number, block_version` for on-chain tables, `synced_at`/`timestamp`/`snapshot_time` for API-sourced — `DESC`, then `processing_version DESC`. NEVER use `build_id` to pick latest: it appears in no unique constraint and one `build_id` spans many sync cycles, so ordering by it picks an arbitrary cycle and mixes values across cycles (manufactures fake anomalies).
- Interpreting numeric columns: a column's name and magnitude don't determine its unit or scale — verify against the column `COMMENT` (psql `\d+ <table>`) or the domain entity doc before computing, aggregating, or flagging an anomaly. Conventions vary per column: raw native-decimal ints (scale by `token.decimals`), column-specific fixed-point (`maple_loan_collateral.asset_value_usd` = per-unit USD price ×1e8, not a total; `maple_loan_state.acm_ratio` = ratio ×1e6), already-normalized decimals (`onchain_token_price.price_usd`), or values that aren't what the name implies (`allocation_position.scaled_balance` = interest-free reading, not the balance). A value repeated across rows is usually correct (one per-unit price per asset per snapshot), not corruption.
- Document every new table and column with `COMMENT ON` in the same migration that creates it — these are the catalogue's source of truth and what the "Interpreting numeric columns" rule above reads. A `--` inline comment is not enough; it is invisible to `\d+` and the metadata catalogue. Match the established style from `20260609_120000_add_schema_comments.sql`: a `[Type]` tag (`Dimension` | `Configuration` | `Operational` | `Hypertable`) on the table; per-column `Roles` (`PK` | `FK→table.col` | `Derived` | `Partition` | `Audit`); and, for any numeric column, its exact unit/scale (raw native-decimal int vs fixed-point ×1eN vs normalized). A column whose unit/scale is not self-evident from its type MUST state it.
- Read-then-write races: when an insert decision depends on a prior read of the same key (read-latest-then-insert, MAX(version)+1, append-on-change), serialize concurrent writers with `pg_advisory_xact_lock` on the natural key — `ON CONFLICT` alone cannot guard a decision made before the insert (ADR-0002 §3); acquire locks in sorted key order to stay deadlock-free.
- A `BEFORE INSERT` trigger function that runs a per-row lookup against a hypertable — every `assign_processing_version_*` function does — must include `SET plan_cache_mode = 'force_custom_plan'` in the `CREATE FUNCTION` that declares it, in the same migration: plpgsql switches the cached lookup to a generic plan after ~5 executions, and a generic plan prunes chunks only where TimescaleDB's `ChunkAppend` can still exclude them at runtime — a `MAX(...)` lookup plans as a `Merge Append` and fans out over every chunk — so insert cost grows with the table's total chunk count (measured 4,410 ms vs 148 ms for one 721-row batch at ~2,000 chunks). The trigger fires before `ON CONFLICT` resolves, so that floor is paid even for the rows the insert then discards. `CREATE OR REPLACE FUNCTION` resets a function's settings, so re-declare the SET whenever you replace one of these functions; `TestProcessingVersionTriggersForceCustomPlan` enumerates `pg_proc` and fails if any of them lacks it (VEC-541, ADR-0002 §3).
- NEVER modify an existing migration file in `stl-verify/db/migrations/`. Migrations are immutable once applied — the migrator tracks checksums and will reject modified files. Always create a new migration file for fixes or additions.
- Filename format: `YYYYMMDD_HHMMSS_description.sql`; plain SQL, applied automatically in order.
- Every migration must self-register: end it with `INSERT INTO migrations (filename) VALUES ('<filename>') ON CONFLICT (filename) DO NOTHING;` or it re-runs on every invocation. Don't mask that with an idempotency guard.
- Every time-series table must get a hypertable + compression policy + S3 tiering policy in the **same** migration that creates it. Exception: sparse governance/config-event tables — those writing on the order of rows per day or less (e.g. `morpho_adapter_membership`, `morpho_vault_cap`, `morpho_vault_fee`) — may be plain tables at maintainer discretion, because chunking, compression and tiering buy nothing at that rate. The decision and its rationale must be stated in the table's `COMMENT`, and the append-only + `processing_version`/`build_id` + advisory-locked trigger requirements still apply in full.
- Role admin vs object grants: role-level ops (`CREATE ROLE`, `ALTER ROLE … SET`, role-to-role membership grants) require superuser and belong in the infra repo's `bootstrap-db.sh`. Migrations run as `stl_migrator` (CREATEROLE only) and hold object-level grants only (`GRANT … ON <object> TO <role>`, `ALTER DEFAULT PRIVILEGES`). Rule: a role named on the left of ALTER/GRANT/DROP = bootstrap; object on left, role on right = migration.
