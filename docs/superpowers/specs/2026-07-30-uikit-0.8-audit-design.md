# Auditing and adopting uikit `0.8.0-dev` in `stl-verify/ts/ui`

Date: 2026-07-30
Status: approved, in implementation

## Goal

`stl-verify/ts/ui` consumes `@archon-research/*` at `0.7.0`. Upstream PR
[archon-research/uikit#58](https://github.com/archon-research/uikit/pull/58) rewrites the
design system: a full semantic token layer, token-driven recipes replacing inline styles,
and a set of new primitives. Two outcomes are wanted:

1. Adopt it in stl — including a visual re-tune onto the new type scale and surface ramp.
2. Produce findings that improve uikit, in the manner of
   `~/Code/synlang-exploration/examples/er-live-data/ui-uikit/FINDINGS.md`.

## Target version

`0.8.0-rohit-ds-tokens-and-primitives.1`, published to npm under the `dev` dist-tag, for
all eight `@archon-research/*` packages. It supersedes an earlier
`1.0.0-rohit-ds-tokens-and-primitives.1` build; the eventual release is not a major bump.

The branch has been force-rewritten more than once during this work, so SHAs quoted in
prior findings documents may not resolve. Findings must name the **published version**
they were measured against, not a branch SHA.

## Scope decisions (agreed up front)

| Decision | Choice |
|---|---|
| Migration ambition | Full adopt **plus** visual re-tune onto the new scale and ramp |
| Local semantic token layer | Delete tokens that collide with upstream; keep only genuine gaps, and report each kept token as an upstream gap |
| Release lag | Audit strictly what is installable from the registry. Do **not** link `~/Code/uikit` |
| Findings destination | Scratchpad document only; nothing committed to either repo, nothing posted upstream |
| Live-data verification | Real data via the local API |
| Upstream fixes | Findings only — all code changes land in stl |

## Methodology rule

Every behavioural claim about uikit must be verified against the **installed/published
`dist/`**, never against `~/Code/uikit/packages/*/src/`. This is a lesson from the prior
audit: its "Pass 6" measured a locally linked build and consequently recorded two findings
as closed that a registry consumer still hit. Reading upstream source to understand intent
is fine; citing it as evidence of current behaviour is not.

## Constraint that shapes the plan

Parallelism is safe for reading and analysis, dangerous for writing. Fan-out therefore
lives in the audit and verification phases. Implementation is parallel only where file
ownership is provably disjoint, and the composition root is owned by one actor.

## Phases

### Phase 0 — Baseline, then install (serial)

Ordering is load-bearing: the running dev server *is* the `0.7.0` baseline, and it is gone
the moment `package.json` changes.

1. Capture the baseline: full-page stills plus a computed-style census, across both themes
   and five states (dashboard, rrc, activity, drawer, activities).
2. Bump the eight packages, `npm install`, `npm run prepare`, restart Vite and clear the
   Vite dep cache. A stale build makes a fixed finding look open, or an open one look
   fixed.
3. Unblock the two known breakages and record the full failure inventory.

**Known blockers, verified before starting:**

- `panda.config.ts` defines a 15-token local semantic layer over `{colors.gray.*}`.
  Upstream renames `gray.*` → `neutral.*`, so the config cannot resolve.
- The config has no `staticCss` key. Published components build recipe class names as
  runtime template strings (`` `badge--variant_${variant}` ``) and no component calls a
  recipe function, so Panda's static extraction cannot see the variants. Without
  `staticCss`, **no design-system recipe CSS is emitted at all**. The fix is to spread the
  exported `designSystemStaticCssRecipes`.

### Phase 1 — Read-only audit, 5 agents in parallel

Each agent writes exactly one findings file to a disjoint path and edits nothing else.
Each receives the dedupe ledger from A6 and must suppress anything already reported unless
stl's case adds new information. Findings need a `file:line`, evidence from the installed
`dist/`, and a falsifiable check.

| Agent | Slice |
|---|---|
| A1 | Tokens and Panda config: local-vs-upstream token map with resolved values per theme, dead refs, `staticCss`, hardcoded colors, DESIGN.md drift |
| A2 | Component adoption map: each local component against the new primitives; frozen API signatures for Phase 2 |
| A3 | DataTable: breaking changes, new `align`/`density`/`meta.mono`, URL-synced table state |
| A4 | Charting: the `chart.*` token family, 1.0-era API deltas, whether `Sparkline` replaces hand-built charts |
| A5 | Typography and density measurement: census diff against baseline, both themes, surface ramp per nesting level |

A6 (prior-art ledger and release integrity) runs during Phase 0 because its output is an
input to A1–A5.

### Phase 2 — Implementation (sequenced, then parallel)

C1 lands alone first because tokens are the foundation. C2/C3/C4 then run in parallel
against A2's frozen API contract, with exclusive file ownership. `App.tsx` is the
composition root every slice touches and is owned by the primary agent, last.

| Agent | Owns exclusively |
|---|---|
| C1 | `panda.config.ts`, `index.css`, `DESIGN.md`, hardcoded-color sites |
| C2 | `src/components/shared/*` and its barrel |
| C3 | `src/data-table/*`, `AllocationGrid.tsx` |
| C4 | `RiskDetailDrawer.tsx`, `BottomPanel.tsx`, `tabs/*` |

### Phase 3 — Verification, 4 agents in parallel

Visual diff against baseline; happy-path flows including URL-sync round-trip; performance
under live updates plus emitted-CSS size (the `staticCss` spread emits every recipe, a cost
the smaller prior consumer could not reveal); and the CI gate — `lint`, `format:check`,
`type:check`, `build`.

### Phase 4 — Synthesis

A findings document naming the measured published version, separating what the upgrade
closed, what stl worked around locally and why, new upstream findings, already-known items
corroborated by a second consumer, and operational findings. Plus a decisions list.

## Environment notes

- Vite binds `127.0.0.1:5473` and is reached through caddy at `https://stl.localhost`.
  It is not on `:5173`.
- Theme is `data-theme` on `<html>`, driven by `localStorage.archon-theme`. A legacy
  `theme` key is also present.
- The local API returns 500 when requests overlap: 8/8 sequential succeed, 5 of 6
  concurrent fail. The dashboard fires roughly six `/v1` calls on mount, so this is hit in
  normal use. Capture must retry; this is an incidental finding, not a uikit one.
- Playwright is not a stl dependency. Point it at an install that already has browsers,
  as the prior consumer's probe does.

## Out of scope

Fixes to the uikit repository, changes to the Go service or Python API, and unrelated
refactoring of the stl UI.
