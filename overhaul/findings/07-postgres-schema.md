# 07 — PostgreSQL adapter and schema

Area: `stl-verify/internal/adapters/outbound/postgres`, `stl-verify/db/migrations`,
`stl-verify/db/migrator`, `cmd/util/{migrate,generate-er}`, `internal/testutil` DB layer.

## 1. Area map

One flat Go package (`postgres`, 36 non-test files) holds 26 repository types, one
`TxManager`, one pgx pool factory (`db.go`) and one pgx tracer (`query_telemetry.go`).
Each repository is asserted against an interface in `internal/ports/outbound/` and
constructed in a `cmd/*/main.go`. Schema lives in 128 hand-written `.sql` migrations
applied by `db/migrator` (409 lines) from `cmd/util/migrate` at every binary start and by
`internal/testutil/templatedb.go` when building the test template database.

```
cmd/<binary>/main.go
   └─ postgres.NewDBPool(DBConfig) ──> *pgxpool.Pool ──┬─> postgres.NewTxManager
                                       (queryErrorTracer)│
   └─ postgres.New<X>Repository(pool[,txm][,tokenRepo],logger,buildID[,batchSize])
          │  implements outbound.<X>Repository  (44 port methods take pgx.Tx)
          ▼
   internal/services/<one service>          <- almost always exactly one caller
          │
          ▼   pgx.Batch | strings.Builder VALUES | unnest()   (no COPY anywhere)
     Postgres/TimescaleDB: 128 tables, 25 hypertables
          ▲
   db/migrator.ApplyAll  <- 128 .sql, checksum-verified, sort.Strings order
   testutil/templatedb.go: sha256(all migrations)+templateFormat -> template DB -> CREATE DATABASE ... TEMPLATE
```

Two things sit *beside* the schema and matter: `data_quality/schemamaster/schema_master.json`
(2,256 lines, embedded, conformance-tested against the live schema) and
`docs/entity_relation.md` (generated by the 807-line `cmd/util/generate-er`, abandoned).

### F07.1 — Append-only is the documented default but the *database* default is the opposite, and the adapter follows the database

**Strength**: Strong
**Files**:
- `stl-verify/db/migrations/20260122_140100_create_app_roles_and_privileges.sql:71`
- `stl-verify/db/migrator/append_only_grants_integration_test.go:26-37`
- `stl-verify/internal/adapters/outbound/postgres/blockstate_repository.go:342, 392, 613, 1124`
- `stl-verify/db/migrations/AGENTS.md` (converted list)

**Problem**: `db/migrations/AGENTS.md` states "Append-only is the DEFAULT, for every table —
not just the converted set." The schema says the reverse:

```sql
-- 20260122_140100_create_app_roles_and_privileges.sql:71
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO stl_readwrite;   -- ALTER DEFAULT PRIVILEGES
```

Every new migrator-owned table is born with full DML for the app role; append-only is
opt-out, one `REVOKE` at a time. ~26 of 128 tables carry a REVOKE. The enforcement is
split across **three disjoint mechanisms with three separate lists**:

1. `convertedAppendOnlyTables` (append_only_grants_integration_test.go:26) — 8 tables,
   asserted by `TestConvertedTablesAreAppendOnly`.
2. Reference tables — a `FOREACH` REVOKE loop in
   `20260630_130000_create_reference_tables.sql:609-615` plus `entity_master`,
   `security_master`, `entity_ref_codes`, `security_instrument_bridge`; asserted by a
   *different* test (`db/migrator/reference_table_immutable_integration_test.go`, 46 lines).
3. `maple_pool_meta`, `maple_loan_meta`, `maple_sky_strategy_meta`
   (`20260627_120000:…`), `prime_proxy` (`20260825_120000_create_prime_proxy.sql`) —
   REVOKE'd, in **no** list, asserted nowhere.

The doc's list is already stale: it names 7 tables; the test names 8 (it added
`oracle_asset` for `20260901_120000`, the doc did not).

The most reorg-critical table is the worst offender. `block_states` is a hypertable and
its lifecycle flags are rewritten in place at four sites:

```go
blockstate_repository.go:342  `UPDATE block_states SET is_orphaned = TRUE WHERE chain_id = $1 AND hash = $2`
blockstate_repository.go:392  `UPDATE block_states SET is_orphaned = FALSE WHERE chain_id = $1 AND hash = ANY($2)`
blockstate_repository.go:613  `UPDATE block_states SET is_orphaned = TRUE WHERE chain_id = $1 AND number > $2 AND NOT is_orphaned`
blockstate_repository.go:1124 `UPDATE block_states SET block_published = TRUE WHERE chain_id = $1 AND hash = $2`
```

AGENTS.md names exactly this shape as forbidden: "a close block, a de-registration, an
`is_active` flag are observations like any other and are appended". `is_orphaned` carries
no version tuple, so the reorg history of a block is unrecoverable and a replayed
backfill's last write wins.

Similarly, the doc forbids the no-op `DO UPDATE SET id = t.id` trick outright — and it is
used at five sites on unconverted tables:
`fluid_vault_repository.go:74`, `maple_loan_repository.go:92, 230, 384, 487`, plus a
variant `DO UPDATE SET protocol_id = EXCLUDED.protocol_id` at `morpho_repository.go:56`.
`morpho_repository.go:349-411` gets it right (`DO NOTHING` + follow-up SELECT) and its
doc comment explains why — because on `morpho_adapter` the wrong form is a *runtime*
error. Correctness here tracks the grant, not the rule.

**Proposed change**:
1. Flip the default: `ALTER DEFAULT PRIVILEGES … GRANT SELECT, INSERT` only, and require a
   migration to explicitly grant UPDATE with a ticket citation. Then the doc's stated
   default and the DB agree, and every existing exception surfaces at once.
2. Replace the three hand-maintained lists with one enumeration derived from the catalogue:
   assert `stl_readwrite` holds no UPDATE/DELETE on any table *except* a small
   `sanctionedUpdateChannels` allowlist. The comment at
   append_only_grants_integration_test.go:23 rejects enumeration because "the rest of the
   schema is still being converted" — invert it and the list shrinks monotonically instead
   of growing in three places.
3. Version `block_states` lifecycle: replace `is_orphaned`/`block_published` with appended
   `block_state_observation` rows and make "canonical at height N" a query. Land it behind
   the existing `BlockStateRepository` port, which already has a second (memory) adapter.
4. Convert the five `DO UPDATE SET id = t.id` sites to `DO NOTHING` + SELECT, matching
   `adapterIdentityID`.

**Benefits**: One enforcement point instead of three lists plus reviewer vigilance. Reorg
rollback and replay-order independence for `block_states` — currently the only table where
a reorg is *destructive*. New tables become correct by default.
**Risk / migration**: (1) and (2) are mechanical and CI-visible. (3) is the real work: the
watcher reorg path, `FindGaps`, and `data_validator` all read `is_orphaned`; land it as a
derived `block_states_current` cache first (the sanctioned `*_current` pattern already
exists) so readers do not change, then flip the writer.
**Size**: (1)+(2)+(4) M; (3) L.
**Depends on / enables**: enables F07.2 (a single append-on-change seam has one rule to obey).

### F07.2 — Three separate implementations of "advisory-lock, read latest, append on change"; the generic one has two callers

**Strength**: Strong
**Files**:
- `postgres/append_on_change.go:29-64` (the generic helper)
- `postgres/curve_repository.go:552-563` (batch pre-lock), `:598-660`, `:717-782` (the 2 callers)
- `postgres/uniswap_v3_repository.go:443-620` (bulk hand-roll)
- `postgres/morpho_repository.go:430-503` (third hand-roll)

**Problem**: `AppendOnChange[T]` exists as a named seam for the read-then-write race that
ADR-0002 §3 mandates guarding. It has exactly two callers, both in `curve_repository.go`.
The other two tables that need the same invariant each rebuilt it:

- `uniswap_v3_repository.go` split it into `lockTickKeys` (:470-487, `unnest()` batch
  lock), `readLatestTicks` (:495-549, `DISTINCT ON` batch read), `insertChangedTicks`
  (:559-605, `pgx.Batch`). Its own comment concedes the equivalence: "the per-tick
  decision (insert vs skip) is byte-for-byte the same as the old per-tick AppendOnChange
  path" (:552-554).
- `morpho_repository.go` split it into `lockAdapterKey` (:496-503), `membershipAt`
  (:443-459), `assertionAppends` (:430-438), `appendMembership` (:465-489).

The advisory-lock statement itself is written out four times verbatim:

```go
`SELECT pg_advisory_xact_lock(hashtextextended($1, 0))`
// append_on_change.go:45, curve_repository.go:559, morpho_repository.go:499
// + the unnest() variant at uniswap_v3_repository.go:478-481
```

Curve also hand-rolls a pre-lock loop (`distinctSortedConfigPoolIDs`, :578-595) that
re-acquires the same keys `AppendOnChange` will take again — with a 5-line comment
explaining the reentrancy — because the helper only locks one key. `uniswap_v3` wrote
`distinctSortedTickKeys` (:611-625) with the comment "mirrors curve's
distinctSortedConfigPoolIDs".

The batched shape is the *dominant* one (one round-trip per phase vs "hundreds of
round-trips under the advisory locks", uniswap_v3:432-434), yet it is the one with no
shared implementation. Every new versioned table pays this again, and the lock-key domain
rule ("deliberately distinct from the pv trigger's key") is re-explained in three long
comments (curve:550-555, uniswap_v3:465-472, morpho:492-495) instead of once.

**Proposed change**: promote the batch form to the seam and delete the single-key one:

```go
// One round-trip per phase; keys are locked in sorted order.
func AppendChanged[K comparable, T any](ctx, tx, spec AppendSpec[K, T]) error
// AppendSpec: LockDomain string; Key func(T) K; SortKey; ReadLatest(ctx,tx,[]K)(map[K]V,error);
//             Changed(prior V, cand T) bool; Insert(*pgx.Batch, T)
```

`ReadLatest` becomes one `DISTINCT ON … JOIN unnest(...)` builder parameterised by table +
key columns + version columns, since all three orderings are the documented
`block_number DESC, block_version DESC[, log_index DESC], processing_version DESC`.
Migrate curve (2 callers) and morpho onto it; uniswap_v3 becomes the reference caller.

**Benefits**: the lock-domain invariant, the latest-row ordering and the round-trip
budget become properties of one module, so the next versioned table gets them free rather
than by copying 130 lines. Locality: ~350 lines of near-duplicate lock/read/insert
plumbing collapses to one file plus three specs. Tests: one deadlock/race suite instead of
the per-table ones now split across `processing_version_concurrency_integration_test.go`
(986 lines) and `current_position_tables_integration_test.go` (935 lines).
**Risk / migration**: The semantics are subtle (block-free lock keys, reorg
re-observation must always insert even when unchanged, per-key in-batch uniqueness
assumptions). Land the generic helper with uniswap_v3 as the only caller first — its tests
are the strictest — then move morpho, then curve.
**Size**: L.
**Depends on / enables**: enabled by F07.1; enables F07.3.

### F07.3 — No shared query/scan/batch layer: 48 hand-written scan loops, 17 batch sites, 5 close-error conventions, 3 bulk-write strategies

**Strength**: Strong
**Files**: package-wide; representative:
- `postgres/position_repository.go:103-119` vs `:172-185` (same file, two conventions)
- `postgres/helpers.go:58-78` (`collectBatchRows`, the one shared helper)
- `postgres/uniswap_v3_repository.go:593-601`, `postgres/prime_capital_stack_repository.go:101-110`

**Problem**: the package has 48 `for rows.Next()` loops and zero uses of pgx v5's
`pgx.CollectRows`/`pgx.RowTo*`. Every one repeats Query → `defer rows.Close()` → declare
locals → `Scan` → append → `rows.Err()`, ~12 lines each (~575 lines total). Nothing is
wrong with any single one; the cost is that a column added to a table means editing the
declaration block, the `Scan` arg list and the struct assembly in each loop by hand.

Batch draining is worse. 17 `SendBatch` sites and five different close-error policies —
two of them in **adjacent functions of one file**:

```go
// position_repository.go:105-113  (SaveBorrowers)
if _, err := br.Exec(); err != nil {
    innerErr := br.Close()
    if innerErr != nil {
        return fmt.Errorf("failed to save borrower record %d: %w; additionally, failed to close batch: %v", i, err, innerErr)
    }
    return fmt.Errorf("failed to save borrower record %d: %w", i, err)
}

// position_repository.go:174-178  (SaveBorrowerCollateral) — same shape, error dropped
if _, err := br.Exec(); err != nil {
    br.Close()          // return value silently discarded
    return fmt.Errorf("failed to save collateral record %d: %w", i, err)
}
```

The other three: `_ = results.Close()` then a second checked `Close()` (7 sites:
allocation:139/148, prime_capital_stack:104/108, prime_capital_stack_allocation:101/106,
prime_debt:125/129, prime_reference_position:99/104, token_total_supply:95/104,
prime_balance_sheet:99/107); `defer …closeErr != nil && err == nil` (5 sites: helpers:63,
event:78, maple_satellite:152, curve:487, uniswap_v3:389); and `errors.Join`
(uniswap_v3:595). Only `helpers.go:58 collectBatchRows` is shared, used by exactly two
repositories (token:88, user:85).

Bulk writes use three strategies with no stated rule and **no `COPY` anywhere**:
`pgx.Batch` (17 sites), hand-built multi-row `VALUES` via `strings.Builder` (9 files), and
`unnest()` arrays (uniswap_v3 only). Of the 9 `strings.Builder` files, 6 use the
`writeValuesPlaceholders` helper (helpers.go:143) and 4 hand-roll the same `$%d` loop
anyway:

```go
onchain_price_repository.go:250   sb.WriteString(fmt.Sprintf("($%d, $%d, $%d, $%d, $%d, $%d, $%d)", …))
offchain_price_repository.go:181  sb.WriteString(fmt.Sprintf("($%d, $%d, $%d, $%d, $%d, $%d, $%d)", …))
user_repository.go:166            sb.WriteString(fmt.Sprintf("($%d, $%d, $%d, NOW())", …))
protocol_repository.go:132        // 27 placeholders on one line
```

Same story for sorting: `sortedCopy`/`sortedByBytesKey` (helpers.go:112/120) are used by
maple (9×), fluid_vault (2×), token, user — and 10 other files call `slices.SortFunc`
in place with their own comment about ADR-0002 lock ordering.

**Proposed change**: one `internal/adapters/outbound/postgres/sqlx` (or extend
`helpers.go`) providing:
- `queryRows[T](ctx, q Querier, sql string, args…, scan func(pgx.Row) (T, error)) ([]T, error)`
  wrapping the Query/Close/Scan/Err skeleton once, or adopt `pgx.CollectRows` directly.
- `runBatch(ctx, tx, *pgx.Batch, kind string, drain func(pgx.BatchResults, int) error) error`
  as the single close-error policy, absorbing all 17 sites.
- `insertRows[T](ctx, q, table string, cols []string, rows []T, bind func(T) []any, conflict string)`
  that picks `unnest()` for large batches and chunk-splits on the parameter limit — one
  place to encode the batch-size policy.

**Benefits**: Leverage — a column add stops being a per-site edit. Locality — the
"partial-failure must stop the whole unit of work" rule in AGENTS.md becomes one
enforceable function instead of 17 hand-audited drains (one of which, position:176, drops
the error today). Tests: `repository_benchmark_test.go` and the per-repo batch tests
collapse onto the helper.
**Risk / migration**: Purely mechanical; convert file by file, each PR self-contained.
Start with the 7 `_ = results.Close()` sites (identical shape) and the 4 hand-rolled
placeholder loops.
**Size**: L (4 PRs: scan loops, batch drain, placeholders/sort, unnest inserts).

### F07.4 — Registry get-or-create: one concept, nine SQL idioms, plus two copy-pasted `resolveTokenIDs` and an N+1 where a batch API exists

**Strength**: Strong
**Files**:
- `postgres/protocol_repository.go:56-78`, `token_repository.go:49-96` & `:195-219`,
  `user_repository.go:55-119` & `:170-190`, `receipt_token_repository.go:36-58`,
  `debt_token_repository.go:45-80`, `fluid_vault_repository.go:56-110`,
  `maple_loan_repository.go:80-133`, `morpho_repository.go:45-70` & `:391-418`
- `postgres/allocation_repository.go:260-314` vs `token_total_supply_repository.go:157-185`

**Problem**: "resolve a registry row by natural key, creating it on first sight, return the
id" is the single most repeated operation in the package (chain/token/user/protocol/
prime/oracle FKs are the documented registry contract). It is written nine ways:

| Table | Conflict arm | file:line |
|---|---|---|
| `protocol` | `DO UPDATE SET created_at_block = LEAST(…)` | protocol:67 |
| `token` (batch) | `LEAST(…)` + `updated_at = CASE … END` + `RETURNING id, symbol, decimals` + drift guard | token:77 |
| `token` (single) | same SQL, `RETURNING id`, **no** drift guard | token:205 |
| `"user"` (batch) | `LEAST(first_seen_block)` + `CASE` | user:75 |
| `"user"` (single) | same SQL, no batching | user:106 |
| `user_protocol_metadata` | `DO UPDATE SET metadata = EXCLUDED.metadata, updated_at = NOW()` | user:178 |
| `receipt_token` | `LEAST(…)`, `updated_at = NOW()` | receipt_token:42 |
| `debt_token` | 4× `COALESCE(EXCLUDED, existing)` + `LEAST` + `CASE` | debt_token:54 |
| `fluid_vault`, `maple_*` | `DO UPDATE SET id = <table>.id` (no-op, ×5) | fluid_vault:74, maple:92/230/384/487 |
| `morpho_market` | `DO UPDATE SET protocol_id = EXCLUDED.protocol_id` | morpho:56 |
| `morpho_adapter` | `DO NOTHING` + follow-up SELECT (the documented form) | morpho:391-418 |

Four distinct answers to "what does a conflict mean" (merge earliest block / refresh
nothing / refresh everything / refuse on drift), and `updated_at` is maintained three
ways (`CASE` on block regression, unconditional `NOW()`, not at all). The drift guard
(`scanTokenDrift`, token:180-220) — the one place that catches a registry disagreeing with
a caller about `decimals`, which "would silently mis-scale every downstream amount" — is
wired only into the batch path; the single-row path 130 lines below has a comment
explaining why it opts out.

Batch/single pairs are duplicated wholesale: `GetOrCreateTokens`/`GetOrCreateToken` and
`GetOrCreateUsers`/`GetOrCreateUser` each carry the same 12-line SQL twice.

Then the FK resolution above it is copy-pasted. `AllocationRepository.resolveTokenIDs`
(allocation:260-314) and `TokenTotalSupplyRepository.resolveTokenIDs` (token_total_supply:
157-185) share the package-level `tokenCacheKey` type (allocation:31), the same map
accumulator, the same `"GetOrCreateToken chain=%d address=%s: %w"` error string — and both
call the **single-row** `GetOrCreateToken` in a loop even though
`TokenRepository.GetOrCreateTokens` (token:49) is a batch API used elsewhere
(`aavelike_position_tracker/service.go:911, 997`, `maple_graphql_indexer/service.go:256,
643`). Two N+1s where the batch already exists — and both bypass the drift guard as a
side effect.

**Proposed change**: one `registry` helper in the package:

```go
type Registry[K comparable] struct{ Table, Conflict string; Cols []string; … }
func (r Registry[K]) Resolve(ctx, tx, keys []K, mk func(K) []any) (map[K]int64, error)
```

with exactly one conflict policy — `ON CONFLICT DO NOTHING` + `SELECT` (the form
`db/migrations/AGENTS.md` mandates and `adapterIdentityID` already implements) — plus one
optional `Immutable []string` list checked through the existing
`registryMismatchError` (helpers.go:101) so the drift guard applies on every path.
Delete both `resolveTokenIDs` in favour of one batch call.

**Benefits**: `decimals` drift is caught on every write instead of one of four paths;
`created_at_block` merging has one definition; the doc's append-only rule becomes true for
the registry tables by construction. Removes two N+1s from the hottest indexer path.
**Risk / migration**: `debt_token`'s `COALESCE` merge is genuinely different (partial rows
from two sources) — keep it as a declared exception or model it as two registry keys.
`RETURNING` on `DO NOTHING` needs the follow-up SELECT, which changes round-trip counts;
the morpho comment (:349-360) documents the race analysis already.
**Size**: L.
**Depends on / enables**: shares the batch helper with F07.3; unblocks F07.1(4).

### F07.5 — 28 constructors, no two alike; three of them inject dependencies that are never used

**Strength**: Strong
**Files**: all `postgres/*_repository.go` constructors; `postgres/config.go`;
`cmd/workers/prime-allocation-indexer/main.go:354-355`

**Problem**: side by side, the 28 constructors diverge on every axis at once:

| Axis | Split |
|---|---|
| Return type | `(*T, error)` **14** vs `*T` **14** |
| Nil-pool check | 14 (only the ones returning an error) — the rest accept nil |
| `logger == nil → slog.Default()` | 26 of 28 |
| `logger.With("component", …)` | **7** of 28 (all the `prime_*`/`psm3`/`anchorage` files) |
| Takes `buildID` | 15 |
| Takes `batchSize` | 8, defaulted **two different ways** |
| Takes `*TxManager` | 5 |
| Takes another port (`tokenRepo`) | 2 |
| Takes `chainID` | 1 (`NewBlockStateRepository`) |

`batchSize` has two parallel default mechanisms. Four constructors read the named config:

```go
protocol_repository.go:46  batchSize = DefaultRepositoryConfig().ProtocolBatchSize  // 500
token_repository.go:40     … .TokenBatchSize      // 500
user_repository.go:42      … .UserBatchSize       // 500
position_repository.go:43  … .PositionBatchSize    // 1000
```

and four hardcode the number, ignoring the struct entirely:

```go
fluid_vault_repository.go:41   batchSize = 1000
offchain_price_repository.go:41 batchSize = 1000 // Prices are simple records…
maple_loan_repository.go:44    batchSize = 1000
onchain_price_repository.go:43  batchSize = 1000
```

`RepositoryConfig` (config.go:6-25) is never constructed as a value anywhere — only
`DefaultRepositoryConfig().<Field>` is read. Deletion test: delete it and four named
constants remain. It is a pass-through.

Three repositories are injected with dependencies they never touch:

- `AllocationRepository` (allocation:23-29) holds `pool` **and** `txm`; zero `r.pool` and
  zero `r.txm` references in the file.
- `TokenTotalSupplyRepository` (token_total_supply:24-30) — same, both dead.
- `PrimeBalanceSheetRepository` (prime_balance_sheet:19-23) holds `pool`, unused.

All three are wired in `main.go` (`prime-allocation-indexer/main.go:354-355`,
`reference-capital-indexer/main.go:103`, `reference-capital-backfill/backfill.go:156`), so
the composition root carries arguments that do nothing — and a reader has to grep the whole
file to learn that.

Transaction ownership has four modes with no rule, and several repositories mix them:

| Mode | Repositories |
|---|---|
| A: take `tx pgx.Tx` from caller | 22 files (44 port methods) |
| B: hold pool, `pool.Begin` + `defer rollback` + `Commit` | blockstate (4×), onchain_price (2×), offchain_price, user |
| C: hold `*TxManager`, `txm.WithTransaction` | anchorage (2×), prime_balance_sheet, prime_debt, psm3 |
| D: `pool.Exec/Query`, no transaction | prime, transform_runner, orderbook, blockstate reads |

`token_repository` is A for its two upserts and D for `ResolveTokenSymbol`/
`ListTokensMissingSymbol`; `user_repository` is A for three methods and B for
`UpsertUserProtocolMetadata`. A caller cannot tell from the port which it gets.

**Proposed change**: one constructor shape.


### F07.10 — 13 migration-filename timestamp collisions make apply order depend on the description text
